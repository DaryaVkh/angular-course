# Задача 1. Гонка при загрузке данных (Race Condition)

🟢 **Уровень:** базовый · ⏱ **Время:** 20–30 минут · 📖 **Лекция:** [Разделы 6–7 (`shareReplay`, `take`, работа с HTTP)](../../lecture/RxJS%20%E2%80%94%20%D0%9B%D0%B5%D0%BA%D1%86%D0%B8%D1%8F%20%28Markdown%29.md)

---

## Суть задания

Вы разрабатываете экран настройки подписок в новостном сервисе. При нажатии на кнопку **Open Topic** пользователю открывается модальное окно (`MatDialog`) со списком доступных рубрик (`Politic`, `Culture`, `Nature`), которые загружаются с бэкенда.

Запрос к серверу занимает около **1 секунды**. Если нетерпеливый пользователь нажимает кнопку сразу после открытия страницы — модальное окно открывается **пустым**.

Ваша задача — избавиться от гонки между загрузкой данных и действием пользователя, не создавая при этом лишних сетевых запросов при повторном открытии окна.

---

## Как запустить стенд

Из корня репозитория выполните:

```bash
npm run serve:rxjs-race-condition
```

Откройте `http://localhost:4200`. На карточке вы увидите телеметрию:
- **Статус API** — идёт ли сейчас загрузка справочника;
- **HTTP-запросов отправлено** — сколько раз был вызван метод `fakeGetHttpTopic()`.

## Схема проблемы и целевого поведения

### ❌ Как работает сейчас (императивное поле `this.topics`)

Компонент запускает запрос в `ngOnInit` и складывает результат в обычный массив `this.topics = []`. Метод `openTopicModal()` синхронно читает это поле в момент клика:

```
Время:            0 мс                  300 мс (клик!)         1000 мс
HTTP-запрос:      [subscribe] ────────────────────────────────► (['Politic', 'Culture', 'Nature'])|
this.topics:      []                    []                      ['Politic', 'Culture', 'Nature']
                                        │
Клик пользователя:                      ▼
Диалог открыт с:                        data: { topics: [] }  💥 ПУСТОЕ ОКНО!
```

### ✅ Как должно работать (реактивное ожидание + кэширование)

Клик подписывается на поток данных. Если запрос ещё в полёте — открытие диалога ждёт эмита. Когда ответ получен — он кэшируется, и последующие клики открывают диалог мгновенно без новых сетевых вызовов:

```
Время:            0 мс                  300 мс (клик #1)       1000 мс               1500 мс (клик #2)
topics$ (кэш):    [запрос #1 в полёте...] ────────────────────► ([3 темы в буфере]) ──► (мгновенно из кэша)
                                        │                       │                     │
Клики:                                  └── ждёт первого эмита ─┴─► Диалог (3 темы)   └─► Диалог (3 темы)
Сетевых вызовов:  1                                             1                     1 (новых нет!)
```

## Пошаговое задание

### Шаг 1. Избавьтесь от промежуточного массива `this.topics`

Сейчас `AppComponent` хранит состояние в обычном свойстве `topics: TopicType[] = []` и синхронно передаёт его в `this.dialog.open(...)`.

1. Замените массив `topics` на поток `topics$`, получаемый из `this.topicService.fakeGetHttpTopic()`.
2. Измените метод `openTopicModal()` так, чтобы диалог `TopicModalComponent` открывался **внутри подписки** на `topics$`, когда данные действительно пришли.
3. Позаботьтесь о том, чтобы каждая подписка в `openTopicModal()` автоматически завершалась после получения первого значения (нам нужно открыть диалог ровно один раз на один клик).

**Проверьте в браузере:** перезагрузите страницу и сразу нажмите **Open Topic**. Диалог должен подождать окончания загрузки и открыться сразу с тремя темами!

---

### Шаг 2. Устраните дублирование сетевых запросов

Посмотрите на счётчик **«HTTP-запросов отправлено»** на карточке после выполнения Шага 1.
Закройте модальное окно и нажмите **Open Topic** ещё 2–3 раза.

Если `topics$` — это обычный холодный (Cold) Observable, то каждый вызов `.subscribe()` в `openTopicModal()` будет заново запускать `fakeGetHttpTopic()`, заставляя пользователя каждый раз ждать по секунде и нагружая сервер.

1. Настройте поток `topics$` так, чтобы запрос к `topicService.fakeGetHttpTopic()` инициировался заранее (или при первом обращении), а его последний результат **кэшировался и переиспользовался** всеми последующими подписчиками.
2. Убедитесь, что при многократном открытии и закрытии модального окна счётчик **HTTP-запросов отправлено** остаётся равен `1`.

---

### Шаг 3 (`*`). Скелетон внутри модального окна вместо задержки открытия

В Шагах 1–2 диалог открывается только после того, как данные пришли с сервера. Если пользователь нажал кнопку на 100-й миллисекунде, интерфейс ещё 900 мс никак не реагирует на клик, и только потом всплывает окно.

В реальных продуктах иногда предпочитают другой UX: **открывать модальное окно мгновенно**, а индикатор загрузки показывать уже внутри него:

1. Подумайте, что произойдёт, если передавать в `dialog.open(TopicModalComponent, { data: ... })` не готовый массив `TopicType[]`, а сам кэшированный поток или читать его через `AsyncPipe` / `toSignal` внутри `TopicModalComponent`.
2. *Важно:* если решите поэкспериментировать с этим шагом, убедитесь, что автотесты (`app.component.spec.ts` и `app.component.cy.ts`) по-прежнему проходят, либо верните контракт `data: { topics: TopicType[] }` перед запуском тестов.

## Ограничения

- Не изменяйте задержку и логику в `src/app/topic.service.ts`.
- Не используйте `setTimeout` или `async/await` — задача решается средствами RxJS.
- При открытии диалога в `MatDialog.open` должен передаваться объект `{ data: { topics } }`.

## Подсказки

<details>
  <summary>💡 Подсказка 1 — Почему в исходном коде возникает гонка?</summary>

В исходном коде две независимые точки во времени:
1. В `ngOnInit` запускается `fakeGetHttpTopic()`, который выдаст массив только через `1000 мс`.
2. В `openTopicModal()` диалог открывается синхронно с тем, что лежит в `this.topics` прямо сейчас (`[]`).

Чтобы связать открытие диалога с моментом готовности данных, само открытие `this.dialog.open(...)` должно происходить в колбэке `.subscribe(...)` потока тем.
</details>

<details>
  <summary>💡 Подсказка 2 — Какой оператор раздаёт закэшированный ответ новым подписчикам?</summary>

Вспомните раздел 6 лекции про мультикастинг:
- Оператор `shareReplay({ bufferSize: 1, refCount: true })` превращает холодный поток в горячий с буфером на 1 последнее значение.
- Если прогреть поток или подписаться на него при первом запросе, все следующие подписчики мгновенно получат сохранённый в буфере массив тем без повторного запуска `timer(1000)`.
</details>

<details>
  <summary>💡 Подсказка 3 — Как начать загрузку сразу при старте приложения, но не плодить подписки?</summary>

Вы можете объявить поле `readonly topics$ = this.topicService.fakeGetHttpTopic().pipe(...)` с оператором кэширования.
Если вы хотите, чтобы загрузка стартовала сразу при инициализации компонента (а не только в момент первого клика), можно инициировать подписку в `ngOnInit()` (или использовать `shareReplay`), а в `openTopicModal()` брать одно значение из `this.topics$.pipe(take(1))` и открывать диалог.
</details>
