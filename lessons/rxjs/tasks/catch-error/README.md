# Задача 2. Живучесть потока: обработка ошибок (`catchError`)

## Суть задания

В реальных приложениях формы поиска, фильтрации и отправки команд часто связывают с потоком пользовательских действий (`submit$ = new Subject<void>()`), который слушается на протяжении всей жизни компонента.

Но у контракта Observable есть жёсткое правило: **уведомление `error` является терминальным**. Если внутренний HTTP-запрос упадёт с ошибкой `404` или `500` и эта ошибка всплывёт в основной пайплайн `submit$`, то подписка на кнопку отправки **навсегда закроется**. Пользователь исправит опечатку в поле ввода, нажмёт кнопку «Fetch» ещё раз — и не произойдёт вообще ничего.

Ваша задача — изолировать ошибку сетевого запроса так, чтобы основной поток `submit$` оставался живым после любого количества сбоев.

Из корня репозитория выполните:

## Схема проблемы и целевого поведения

### ❌ Как работает сейчас (ошибка убивает внешний поток)

Неперехваченная ошибка внутреннего `http.get(...)` пробивает `concatMap` и завершает всю цепочку `submit$`:

```
submit$:     ──(click: posts)──────(click: foo)────────(click: comments)──►
                    │                   │                      │
inner HTTP:         └──►──(200 OK)|     └──►── ✕ (404 Error)   (игнорируется — подписка мертва!)
                                               │
Результат:   ──────({ id: 1 })─────────────────✕ (ТЕРМИНАЛЬНЫЙ ERROR)
Статус:      [● Активен]                 [✕ Аварийно закрыт навсегда]
```

### ⚠️ Частая ловушка: `catchError` на внешнем потоке

Если поставить `catchError` в основной `.pipe()` **после** `concatMap`, он перехватит ошибку, заменит поток на резервный `of(...)` и тут же **успешно завершит (`complete`)** всю цепочку! Новые клики всё равно перестанут работать.

### ✅ Как должно работать (изоляция во внутреннем потоке)

Ошибка перехватывается **внутри** внутреннего потока HTTP-запроса и заменяется безопасным значением (`next` + `complete` только для этого конкретного запроса). Внешний поток `submit$` даже не узнаёт об аварии и продолжает ждать следующих кликов:

```
submit$:     ──(click: posts)──────(click: foo)─────────────(click: comments)──►
                    │                   │                        │
inner HTTP:         └──►──(200 OK)|     └──►── ✕                 └──►──(200 OK)|
                                               └─► catchError
                                                   ──(fallback)|
                                                       │
Результат:   ──────({ id: 1 })─────────────────(fallback)────────({ id: 1 })───►
Статус:      [● Активен]                 [● Активен]             [● Активен]
```

## Пошаговое задание

### Шаг 1. Воспроизведите «смерть» потока в браузере

1. Запустите стенд и нажмите **Fetch** для `posts` — в блоке ответа появится JSON поста, а статус в шапке останется зелёным (`● Поток submit$ активен`).
2. Выберите пресет `foo (404 Error)` и нажмите **Fetch**.
3. Обратите внимание на бейдж в правом верхнем углу: он стал красным (`✕ Поток submit$ аварийно закрыт`).
4. Снова выберите `posts` и нажмите **Fetch** — сетевой запрос больше не отправляется.

---

### Шаг 2. Изолируйте ошибку HTTP-запроса

Отрефакторите пайплайн в `src/app/app.component.ts` так, чтобы:

1. При возникновении HTTP-ошибки она перехватывалась до того, как попадёт во внешний поток `submit$`.
2. Ошибка не терялась бесследно: выведите её в консоль и верните резервный поток с информацией об ошибке (чтобы она отобразилась в `this.response` на экране).
3. Подписка на `submit$` создавалась только один раз в `ngOnInit` (не пересоздавайте подписку вручную при каждом клике).
4. После ошибки `404` статус потока оставался `alive`, а следующий запрос к `posts` или `comments` успешно загружал данные.

---

### Шаг 3 (`*`). Защита от пустого ввода и форматирование ответа об ошибке

Прокачайте пайплайн ещё на два шага, приблизив его к реальному продакшен-коду:

1. **Фильтрация пустых строк:** если пользователь стёр текст в поле ввода (или ввёл только пробелы) и нажал **Fetch**, HTTP-запрос вообще не должен отправляться. Подберите подходящий оператор фильтрации для потока `submit$`.
2. **Читаемая карточка ошибки:** вместо вывода сырого `HttpErrorResponse` в резервном потоке сформируйте аккуратный объект, например `{ error: true, status: error.status, message: 'Ресурс не найден' }`, чтобы пользователю было понятно, что произошло.

## Ограничения

- Не переносите `.subscribe()` внутрь обработчика клика или `ngSubmit` — поток `submit$` должен оставаться реактивным конвейером.
- Не используйте `try / catch` или `fetch` — используйте `HttpClient` и операторы RxJS.

## Подсказки

<details>
  <summary>💡 Подсказка 1 — Почему поток закрывается?</summary>

В RxJS любой Observable следует контракту `next* (error | complete)?`. Когда `this.http.get(...)` возвращает `404`, он генерирует уведомление `error`. Оператор `concatMap` по умолчанию пробрасывает ошибку внутреннего потока во внешний — и внешний поток тоже завершается с ошибкой.
</details>

<details>
  <summary>💡 Подсказка 2 — Где именно должен стоять оператор перехвата?</summary>

Сравните две структуры:

1. Внешний перехват (завершает внешний поток после первой ошибки):
   ```ts
   submit$.pipe(
     concatMap(value => this.http.get(...)),
     catchError(err => ...) // ❌ Поздно! concatMap уже умер
   )
   ```
2. Внутренний перехват (завершает только один неудачный HTTP-запрос, сохраняя жизнь `concatMap`):
   ```ts
   submit$.pipe(
     concatMap(value =>
       this.http.get(...).pipe(
         // ✅ Ошибка гасится внутри конкретного запроса
       )
     )
   )
   ```
</details>

<details>
  <summary>💡 Подсказка 3 — Что должен возвращать обработчик в catchError?</summary>

Функция внутри `catchError((error) => ...)` обязана вернуть **новый Observable** (а не просто объект). Чтобы передать объект ошибки в ветку `next` подписчика и отобразить его на экране, оберните его в оператор создания потока из одного значения — `of(...)`.
</details>
