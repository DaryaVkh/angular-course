# Расширенные знания

Здесь разбирается механика графа зависимостей и каждая из пяти задач урока: что именно
ломается, почему и как чинить. Читать после [базовой части](./basics.md).

---

## 1. Как на самом деле работает отслеживание зависимостей

Граф сигналов состоит из узлов двух ролей:

- **producer** — узел, у которого есть значение и версия (`signal`, `computed`, `input`);
- **consumer** — узел, который читает других (`computed`, `effect`, а также шаблон
  компонента: представление — это тоже реактивный потребитель).

Когда consumer выполняется, Angular открывает **реактивный контекст** и записывает в него
каждый прочитанный producer. По окончании прогона старый список зависимостей заменяется
новым.

Из этого следуют три неочевидных факта:

1. Зависимости **динамические**. Не «какие сигналы упомянуты в коде», а «какие успели
   прочитаться за конкретный прогон».
2. Отслеживается **чтение**, а не место объявления. Неважно, читается сигнал прямо в теле
   функции, в трёх вызовах вниз по стеку или внутри метода чужого сервиса — контекст один
   и тот же (динамическая область видимости).
3. Асинхронное чтение **не отслеживается**: всё, что после `await`, `setTimeout` или в
   коллбэке подписки, выполняется уже вне реактивного контекста.

```ts
effect(() => {
  console.log(this.a()); // ✅ зависимость
  setTimeout(() => console.log(this.b())); // ❌ не зависимость
  fetch(url).then(() => console.log(this.c())); // ❌ не зависимость
});
```

`untracked` — явный выход из контекста: значение читается, но зависимость не создаётся.

```ts
effect(() => {
  const id = this.userId(); // зависимость
  const filters = untracked(this.filters); // читаем «текущее», но не подписываемся
  this.analytics.track(id, filters);
});
```

## 2. `bug-in-effect`: пропавшая зависимость

```ts
effect(() => {
  if (this.drive() || this.ram() || this.gpu()) {
    alert('Price increased!');
  }
});
```

Прогон за прогоном:

| Шаг                       | Что прочитано                           | Зависимости после прогона |
| ------------------------- | --------------------------------------- | ------------------------- |
| Первый прогон (все false) | `drive`, `ram`, `gpu`                   | все три                   |
| Отмечен `drive`           | `drive` → `true`, дальше `\|\|` не идёт | **только `drive`**        |
| Отмечен `ram`             | эффект не перезапускается               | —                         |

Виноват не сигнал, а короткое замыкание `||`: как только первый операнд истинный,
остальные не вычисляются, значит не читаются, значит выпадают из списка зависимостей.
Ровно то же самое произойдёт с `&&`, ранним `return`, `if/else` и тернарником.

### Починка 1 — читать всё до ветвления

```ts
effect(() => {
  const extras = [this.drive(), this.ram(), this.gpu()]; // все три прочитаны всегда
  if (extras.some(Boolean)) {
    alert('Price increased!');
  }
});
```

### Починка 2 (бонус задачи) — вынести логику в `computed`

Просто завернуть `||` в `computed` мало: короткое замыкание никуда не денется, а результат
`true → true` не изменится, и потребители не будут уведомлены. Считать нужно то, что
действительно меняется на каждый клик:

```ts
protected extrasCount = computed(
  () => [this.drive(), this.ram(), this.gpu()].filter(Boolean).length,
);

constructor() {
  let previous = 0;
  effect(() => {
    const current = this.extrasCount();
    if (current > previous) {
      alert('Price increased!');
    }
    previous = current;
  });
}
```

Здесь `computed` — это «сколько допов выбрано» (значение), а `effect` — «сообщить
пользователю» (побочное действие). Снятие галочки цену не повышает и алерта не вызывает.

**Правило:** в реактивном контексте сначала читаем все нужные сигналы в переменные, потом
ветвимся. Ленивые операторы и реактивность плохо дружат.

## 3. `function-call-effect`: лишняя зависимость

```ts
effect(() => {
  this.userService.log(this.action() ?? 'No action selected');
});

// user.service.ts (менять нельзя)
log(message: string) {
  console.log(`${this.name()}: ${message}`);
}
```

В `effect` нет ни одного упоминания `name`, но `log` читает `this.name()` **внутри того же
реактивного контекста** — вызов функции контекст не закрывает. В результате `name`
становится полноценной зависимостью, и смена пользователя перезапускает эффект.

Починка — выполнить побочное действие вне контекста:

```ts
effect(() => {
  const action = this.action() ?? 'No action selected'; // зависимость, которую мы хотим
  untracked(() => this.userService.log(action)); // всё внутри — не отслеживается
});
```

Читаемая формулировка правила: **в теле эффекта отслеживаемая часть — только чтение
входных сигналов; сам побочный эффект оборачиваем в `untracked`.** Тогда «случайные»
зависимости из чужого кода перестают влиять на частоту запусков.

Полезно помнить, что тем же способом ловятся зависимости в шаблоне: вызов метода
компонента в интерполяции, читающего сигналы, подписывает на них представление.

## 4. Тайминг эффектов, запись в сигналы, отладка

- Эффекты выполняются не в момент `set`, а позже. Angular различает два вида эффектов:
  **компонентные** (созданы в компоненте, директиве или сервисе компонента) выполняются
  как этап жизненного цикла во время change detection — в них уже безопасно читать входы;
  **корневые** (созданы вне дерева компонентов, например в root-сервисе) выполняются как
  микрозадачи и с change detection не связаны. Несколько записей до момента запуска
  схлопываются в один прогон.
- С Angular 19 запись сигналов внутри эффекта разрешена, опция `allowSignalWrites`
  устарела. Разрешена — не значит рекомендована: связка «эффект пишет сигнал, от которого
  зависит другой эффект» превращает граф в неотлаживаемую цепочку. Для «производного
  состояния с возможностью перезаписи» есть `linkedSignal`, для загрузки данных —
  `resource` / `rxResource`.
- `effect` требует контекста внедрения зависимостей. Вне его (например, в коллбэке) нужен
  явный `injector`: `effect(fn, { injector: this.injector })`.
- Для работы с DOM после отрисовки существует `afterRenderEffect` / `afterNextRender` —
  они выполняются на фазе рендера и не выполняются на сервере.
- Для отладки у `signal`, `computed` и `effect` есть опция `debugName` — имя видно в
  Angular DevTools.

```ts
effect(
  () => {
    /* ... */
  },
  { debugName: 'sync-theme' },
);
```

### `linkedSignal` вместо «эффекта, который что-то сбрасывает»

Классический сценарий: локальное состояние должно сбрасываться при смене входа, но
пользователь может его менять.

```ts
// ❌ эффект пишет сигнал
constructor() {
  effect(() => this.selected.set(this.options()[0]));
}

// ✅ производное состояние, которое можно перезаписать
selected = linkedSignal(() => this.options()[0]);
```

## 5. `forms-and-signal`: у формы и у URL разные источники истины

Шаг `order` устроен так:

```ts
form = new FormGroup({ quantity: new FormControl(1, { nonNullable: true }) });

quantity = toSignal(this.form.controls.quantity.valueChanges, {
  initialValue: this.form.getRawValue().quantity,
});
```

Количество живёт **только внутри формы**, а дальше по маршруту передаётся через query
параметр (`[queryParams]="{ quantity: quantity() }"`). При возврате с checkout параметр в
URL есть, но компонент его не читает — форма создаётся заново со своим значением `1`.

Два момента, на которых обычно спотыкаются:

1. Значения сигнальных входов **недоступны в конструкторе и в инициализаторах полей** —
   вход связывается позже. Поэтому `new FormControl(this.quantity())` не сработает:
   вернётся значение по умолчанию.
2. Query параметр — строка. Без `transform: numberAttribute` в компонент приедет `'3'`:
   умножение отработает за счёт приведения типов, а сложение молча превратится в
   конкатенацию (`'3' + 1 === '31'`).

Решение: сделать URL источником истины при входе на шаг, а форму — редактором этого
значения.

```ts
export default class OrderComponent {
  productId = input('1');
  quantity = input(1, { transform: numberAttribute }); // ← из query params

  form = new FormGroup({
    quantity: new FormControl(1, { nonNullable: true }),
  });

  // форма → сигнал
  private formQuantity = toSignal(this.form.controls.quantity.valueChanges, {
    initialValue: this.form.getRawValue().quantity,
  });

  protected selectedQuantity = computed(() => Number(this.formQuantity()));

  price = computed(() => products.find((p) => p.id === this.productId())?.price ?? 0);
  totalWithoutVat = computed(() => this.price() * this.selectedQuantity());
  vat = computed(() => this.totalWithoutVat() * 0.21);
  total = computed(() => this.totalWithoutVat() + this.vat());

  constructor() {
    // URL → форма
    effect(() => {
      const fromUrl = this.quantity();
      untracked(() => this.form.controls.quantity.setValue(fromUrl));
    });
  }
}
```

`setValue` эмитит `valueChanges`, поэтому `formQuantity` и все `computed` подхватывают
значение из URL; `untracked` защищает от случайных зависимостей внутри вызова формы.

Альтернатива без эффекта — `linkedSignal`, если сделать источником истины сигнал, а форму
синхронизировать в обе стороны:

```ts
protected selectedQuantity = linkedSignal(() => this.quantity()); // сбрасывается при смене URL
// в шаблоне: (change) / valueChanges → selectedQuantity.set(...)
```

Побочный вариант задачи (template-driven формы) сводится к `model()` + `[(ngModel)]`: там
двусторонняя связь уже сигнальная, и весь мост `toSignal` не нужен.

## 6. `pipe-observable-to-signal`: чистый пайп не реактивен

Перевод сервиса делается механически:

```ts
@Injectable()
export class CurrencyService {
  private readonly code = signal('EUR');

  readonly symbol = computed(() => currency.find((c) => c.code === this.code())?.symbol ?? this.code());

  updateCode(code: string) {
    this.code.set(code);
  }
}
```

А вот наивный перевод пайпа — ловушка, о которой предупреждает условие задачи:

```ts
@Pipe({ name: 'currency' })
export class CurrencyPipe implements PipeTransform {
  private currencyService = inject(CurrencyService);

  transform(price: number): string {
    return `${price}${this.currencyService.symbol()}`; // ❌ значение застынет
  }
}
```

Чистый (pure) пайп мемоизируется по аргументам: пока `price` не изменился, Angular
возвращает закешированный результат и `transform` вообще не вызывает. Сигнал, прочитанный
внутри, помечает представление грязным, представление пересчитывается — но пайп отдаёт
старую строку. Реактивность есть, обновления нет.

Рабочие варианты, от лучшего к худшему:

1. **Передать реактивное значение аргументом** — пайп остаётся чистым, зависимость явная:

   ```ts
   transform(price: number, symbol: string): string {
     return `${price}${symbol}`;
   }
   ```

   ```html
   <td>{{ product().priceA | currency: symbol() }}</td>
   ```

2. **Убрать пайп** и посчитать строки в компоненте через `computed` — меньше сущностей,
   всё отслеживается штатно.
3. `pure: false` — работает, но `transform` начинает вызываться на каждом проходе
   проверки изменений. Для таблицы это худший вариант.

Второй скрытый дефект того же приложения — запись состояния в сеттере входа:

```ts
@Input({ required: true }) set product(product: Product) {
  this.currencyService.updateCode(product.currencyCode); // запись при связывании входа
  this.productInfo = product;
}
```

При переходе на `input()` соблазн — заменить сеттер эффектом, который пишет в сервис. Это
и есть та самая «запись сигнала из эффекта». Правильнее убрать изменяемое состояние:
код валюты **выводится** из продукта.

```ts
export class ProductRowComponent {
  product = input.required<Product>();

  private currencyService = inject(CurrencyService);
  protected symbol = computed(() => this.currencyService.symbolOf(this.product().currencyCode));
}
```

Здесь `symbolOf(code)` — чистая функция-хелпер в сервисе (поиск по справочнику валют),
без изменяемого состояния вообще. Если же сервис обязан хранить код валюты, мост от входа
к состоянию — это `linkedSignal(() => this.product().currencyCode)`, а не эффект.

## 7. Чеклист код-ревью сигнального кода

- Производное значение объявлено `computed`, а не сигналом, который обновляют руками.
- В `effect` нет вычисления состояния — только побочные действия, и они в `untracked`.
- Все нужные сигналы прочитаны до ветвлений, `||` / `&&` / ранний `return` не съедают
  зависимости.
- Объекты и массивы обновляются через новую ссылку (`update`, spread), а не мутацией.
- Мост от чужого состояния (форма, роутер, чужой сервис) явный: `toSignal`, `input`,
  `linkedSignal` — а не эффект, который что-то куда-то перекладывает.
- Значения входов не читаются в конструкторе и инициализаторах полей.
- Пайпы и «чистые» функции не читают сигналы скрытно: реактивное значение приходит
  аргументом.
- Загрузка данных по изменению параметра — `resource` / `rxResource`, а не `effect` с
  подпиской внутри.
